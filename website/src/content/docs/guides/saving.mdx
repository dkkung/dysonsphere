title: Saving, reading, loading
description: Export self-describing figures and read the provenance, statistics, and data back out.
---

`ds.save()` is more than a renderer: it embeds provenance, the resolved theme, any statistics, and
your data into the exported files, so every figure is its own lab-notebook entry. `ds.metadata.read()` and
`ds.load()` pull that information back.

## Saving

```python
import dysonsphere as ds

ds.theme()
# ... build `chart` ...

ds.save(chart, "figure")
```

By default this writes `figure.svg` and `figure.json`. Control the outputs with `format=` (any of
`"svg"`, `"png"`, `"json"`, `"html"` - a string or a list) and `background=` (`"light"`, `"dark"`,
or both). A two-background export gets `_light` / `_dark` suffixes; a single background gets clean
names.

```python
ds.save(chart, "figure", format=["svg", "png", "json"], background=["light", "dark"])
ds.save(chart, "figure", format="html")   # a self-contained interactive HTML page
```

The SVG post-processing means a notebook's inline preview (Altair renders straight from Vega-Lite)
can differ subtly from the saved file. `ds.show(chart)` renders a chart *through* the `save()`
pipeline so the preview matches the exported figure exactly.

`show()` styles the preview entirely from the theme, including `transparent` - unlike `save()`,
which defaults to a transparent background so exports composite onto a page. The preview is
returned as HTML wrapping the SVG, so it sits on the notebook's own background just like a bare
Altair chart, and a transparent dark-mode figure stays readable.

The SVG is post-processed for publication: `<g>` wrappers are flattened for Illustrator, axis ticks
and log/power minor ticks are snapped to exact positions, superscript exponents are realigned, and
Latin statistical symbols (*P*, *n*, *F*, *r*, ...) are set in italic per convention - digits,
operators, and Greek symbols (η², ρ, τ) stay upright.

### Fonts

Exports reference fonts by name instead of embedding them, so a saved chart samples the user's system
across a list of fallback defaults. The default, Helvetica Neue, ships with macOS; Windows falls back
to Arial, and Linux distributions fall back to their default sans-serif font. SVGs use the PostScript
name `HelveticaNeue` so they open in the right font in Adobe Illustrator, which doesn't follow the
usual fallback list. To override the default font on any platform, set `theme(font="...")`.

By default, `theme(fontGreek="Symbol")` switches only Unicode Greek letters to the named font in
`show()` and SVG/PNG `save()` output. Latin text, numerals, punctuation, operators, the micro sign
(`µ`), and explicit italic runs keep their surrounding styling; `theme(fontGreek=None)` disables
the switch, and a nonblank custom family name selects another installed font. Unicode characters
remain unchanged in editable SVG text. Interactive HTML and bare Altair output do not receive this
correction. Because fonts are named rather than embedded, a requested family can fall back when it
is unavailable and does not by itself prove compliance with a journal's font requirements.

## What gets embedded

When `saveMetadata=True` (the default), `save()` writes a `dysonsphere` metadata block into all
three formats:

- **provenance** - who/when/what: the user, the script, the source text of the chart expression
  you saved, plus the full rendering environment - the OS, the versions of Python, Altair,
  vl-convert (the renderer), dysonsphere (and any extensions that produced the figure), numpy,
  scipy, and polars - then the machine-identity checksums.
- **theme** - the resolved `ds.theme()` arguments, so the look can be reproduced exactly.
- **statistics** - the structured records from any `ds.stats.comparisons()` / `ds.stats.correlation()` on the
  chart (exact p-values, effect sizes, descriptives).
- **report** - the human-readable version of those statistics.

## What the embedded metadata looks like

This is not hand-waving - here is the actual block from a real save. Take a strip plot with a
Kruskal-Wallis comparison on the classic `cars` dataset:

```python
strip = ds.mark_strip(cars, "Origin", "Miles_per_Gallon", origins)
mpg_comparisons = ds.stats.comparisons(
    cars, "Origin", "Miles_per_Gallon",
    [("USA", "Europe"), ("USA", "Japan")],
    test="kruskal", omnibusVerbose=True, categories=origins,
)
ds.save(strip + mpg_comparisons, "mpg_by_origin", format="json")
```

`ds.metadata.read("mpg_by_origin.json", what="metadata")` returns a `dict` with four keys - `provenance`,
`statistics`, `theme`, and `report`. The **provenance** leads with who/when/what, then the full
rendering environment (the OS and vl-convert pin how text was measured, beyond the library
versions), and ends with the machine-identity checksums:

```json
{
  "user": "dkkung",
  "script": "mpg_by_origin.py",
  "chart": "strip + mpg_comparisons",
  "timestamp": "2026-07-08T22:55:35Z",
  "environment": {
    "os": "macOS-26.5.2-arm64-arm-64bit",
    "python": "3.11.8", "altair": "6.2.1", "vl_convert": "1.9.0.post1",
    "dysonsphere": "3.5.0", "numpy": "2.4.6", "scipy": "1.17.1", "polars": "1.41.2"
  },
  "vegaliteChecksum": "sha256:53a99fe9a0e4ad703751014765e01a7f0860d7d89a78add9d50ead172f7aa9f2",
  "exportIdentifier": "ef49895a-2e06-495a-86d3-7b0f2980cd8b",
  "dataChecksum": ["multiset-sha256:281a94603a8549cda02866679f34c8d0d5ed490d3944c5ab881423ff388b52e8"]
}
```

`chart` is the source text of the `chart` argument, captured verbatim at the `save(...)` call
site - here the composition `strip + mpg_comparisons`; save a plain variable and it records that
variable's name. It is best-effort convenience (omitted where no source is available, e.g. a plain
REPL) - identity belongs to the checksums. The three checksums answer different questions:
`dataChecksum` (one per dataframe, order-independent) is the **data** identity - two charts of the
same numbers match even if drawn differently; `vegaliteChecksum` is the exact **spec content**;
`exportIdentifier` is shared by every file from one `save()` call. The prefixes differ because the
guarantees do: `sha256:` is SHA-256 over the spec's bytes, so anyone can strip `usermeta` and re-hash
the file to check it, while `multiset-sha256:` is a hash of the multiset of row digests - which is
what makes it independent of row order, and what means it cannot be reproduced by hashing the file. A figure produced by an extension (say
`ds.biology.volcano`) additionally records `"dysonsphere-extensions": {"biology": "0.1.0"}` in
`environment` - only extensions that actually built the chart, not merely installed ones.

The **statistics** entry is a list of structured records - exact p-values and effect sizes, not

The **data** itself round-trips too. `ds.metadata.read("mpg_by_origin.json", what="data")` returns the
original 398-row dataframe - every column Altair inlined, including transform columns like
`jitter_x` (the honest data of record), with dysonsphere's own sidecar layers (bracket
coordinates, error bars) filtered out.

## Reading it back

```python
ds.metadata.read("figure.json")                    # the human-readable report (default)
ds.metadata.read("figure.json", what="statistics") # structured records (list of dicts)
ds.metadata.read("figure.json", what="metadata")   # the whole dysonsphere block (shown above)
ds.metadata.read("figure.json", what="data")       # the original DataFrame
```

`ds.metadata.read()` works on JSON, SVG, and PNG for metadata and reports; `what="data"` is JSON-only (only the
JSON carries the full data). `what="data"` returns the user's frame, filtering out dysonsphere's
internal sidecar datasets; pick the output type with `output=` (`"polars"`, `"pandas"`, `"duckdb"`,
or `"records"`).

## Verifying a figure

`ds.metadata.verify()` re-checks a figure against the checksums it carries, with no access to the original
script:

```python
ds.metadata.verify("figure.json")                   # was the spec edited after export?
ds.metadata.verify("figure.png", data=df)             # did this figure come from this data?
ds.metadata.verify("figure.json", data=[counts, meta]) # multi-frame chart
```

It returns a `ds.metadata.VerifyResult` (shown below as its printed representation):

```python
VerifyResult(
    path='figure.json',
    specValid=True,
    dataMatches=True,
    storedDataChecksums=['multiset-sha256:57ae424f2a1d3887eaed57bd8733b7a256d1f6f7370a55cc3458bd14a19f928b'],
    computedDataChecksums=['multiset-sha256:57ae424f2a1d3887eaed57bd8733b7a256d1f6f7370a55cc3458bd14a19f928b'],
    exportIdentifier='0513f023-4667-4367-8883-e8762571811d',
    timestamp='2026-08-03T23:56:06Z',
)
```

| field | |
| --- | --- |
| `specValid` | the spec still hashes to the recorded `vegaliteChecksum` - the file has not been edited |
| `dataMatches` | the frames you passed hash to the recorded `dataChecksum` |
| `storedDataChecksums` | what the file recorded |
| `computedDataChecksums` | what your frames hash to now - the two differ only when `dataMatches` is `False` |
| `exportIdentifier` | the `ds.save()` call that produced the file; every format and background of one save shares it |
| `timestamp` | when that save ran |
| `matches` / `groups` | filled only when comparing a list - see below |
| `.ok` | every check that actually ran passed |

Both checks are tri-state: `None` means the check could not run, which is not a failure - SVG and
PNG carry the checksums but not the spec, so `specValid` is `None` there while `dataMatches` still
works. `.ok` reads `None` as "not a failure" for that reason. Neither row order nor the order
dataframes are passed in affects the result.

When a check fails, the two checksum fields are what tell you which frame diverged:

```python
r = ds.metadata.verify("figure.json", data=edited)
r.ok           # False
r.specValid    # True  - the file itself is intact
r.dataMatches  # False - but it did not come from this data
```

A file whose metadata is gone - screenshotted, or re-saved by a tool that drops it - cannot be
checked at all; `ds.metadata.verify()` raises, because there is nothing left to compare against. What
survives is the trail for the *data*: these checksums are recomputed from content rather than
minted per file, so `ds.metadata.frame_checksum(df)` returns the same value for the same rows forever, and a
dataframe can still be matched against an intact sibling export or a checksum recorded elsewhere.

## Which field answers which question

Three fields in `provenance` look interchangeable and are not:

| question | field |
| --- | --- |
| Is this the same chart? | `vegaliteChecksum` - content identity, unchanged by re-saving |
| Did these files come from one `ds.save()` call? | `exportIdentifier` - shared by every format and background of one save |
| Is this the same underlying data? | `dataChecksum` - unchanged by restyling the chart |

## Comparing figures

Hand `ds.metadata.verify()` a list and it compares them instead of checking one:

```python
ds.metadata.verify(["fig1.json", "fig2.png", "fig3.svg"])
```

```python
matches   {"spec": False, "data": True,  "save": False}
groups    {"spec": {"fig1.json": 0, "fig2.png": 0, "fig3.svg": 1},
           "data": {"fig1.json": 0, "fig2.png": 0, "fig3.svg": 0},
           "save": {"fig1.json": 0, "fig2.png": 1, "fig3.svg": 2}}
```

`matches` is the quick answer - do they all agree. `groups` numbers them when they do not, and
**the same number means the same figure**: above, the first two are the same chart, all three were
built from the same data, and each came from its own save.

Items may be saved files in any format, or Altair charts you have not saved yet - so
`ds.metadata.verify(["published.json", chart])` asks whether the figure your script builds today still
matches the one you published. A chart in memory has no export identity, so `"save"` comes back
`None` for the whole call. `what=` narrows it: `what="data"` asks only about the data.

Reach for `"spec"` first when you want "is this the same chart". Two saves of an identical chart
agree on it but get *different* export identifiers, so `"save"` alone reports a difference for a
figure that was merely re-exported.

:::note
Comparing reads what each file *recorded*, which is what lets a PNG be compared with a JSON - a PNG
carries no spec to re-hash. The cost is that an edited file still compares as the chart it claims
to be; checking a figure on its own is what detects an edit.
:::

## Reproducible exports

Re-running a build script rewrites every figure even when nothing changed, because `timestamp` and
`exportIdentifier` are the only non-deterministic bytes in an export - the checksums are already
stable. For figures committed alongside a manuscript that means every rebuild dirties every file.

Set [`SOURCE_DATE_EPOCH`](https://reproducible-builds.org/specs/source-date-epoch/), the
cross-tool convention for this, to an integer count of UTC seconds:

```bash
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) uv run python build_figures.py
```

Repeated saves of an unchanged figure are then byte-identical. Anchoring it to the last commit is
the idiom worth copying: the recorded time becomes *the commit the figure was built from*, so it
moves when the code moves and holds still when it does not.

Nothing else about the metadata changes - same fields, same shapes. Two values differ:

| | default | pinned |
| --- | --- | --- |
| `timestamp` | the real save time | the instant you supplied |
| `exportIdentifier` | a random UUID, new every save | a UUID derived from the figure's timestamp, spec, and data |

What you give up is real and worth stating: the figure no longer records when the export actually
ran, and two separate saves of identical inputs now share an identifier - identical inputs
producing identical outputs is the whole point. A malformed value raises rather than quietly
falling back to the clock, since a silent fallback would hand you a non-reproducible file while you
believed it was pinned.

## Rebuilding the chart

```python
chart = ds.load("figure.json")            # an Altair object, theme re-applied
spec  = ds.load("figure.json", raw=True)  # the untouched Vega-Lite spec dict
```

`load()` is JSON-only (it needs the full spec) and re-applies the baked theme so the reconstructed
chart renders identically.

The rebuilt Altair object carries **no metadata**: `load()` strips `usermeta` along with `config`,
because Altair's schema rejects some of the theme's config values. So loading a figure and then
checking it does not work - there are no checksums left on the object to check. Verify the file
itself, which is what `ds.metadata.verify()` expects anyway:

```python
ds.metadata.verify("figure.json", data=df)                    # yes - reads the file
ds.metadata.verify(ds.load("figure.json"))                  # no - the object has no metadata
```

`ds.load("figure.json", raw=True)` does keep `usermeta`, since it returns the spec untouched.

## Statistics without a file

`ds.stats.comparisons()` and `ds.stats.correlation()` can surface their report directly:

```python
chart = base + ds.stats.comparisons(df, "group", "value", pairs, test="anova", report=True)
# report=True prints it; saveReport="dir/" writes a timestamped .txt
```

## How the fields map to provenance standards

The field names are dysonsphere's own, but the concepts are not - each has a counterpart in an
established provenance vocabulary:

| dysonsphere | Equivalent |
| --- | --- |
| `user` | W3C PROV `Agent` + `wasAttributedTo`; Dublin Core `dcterms:creator` |
| `script` | PROV `Plan` / `hadPlan` |
| `chart` | no equivalent in any standard |
| `timestamp` | PROV `generatedAtTime`; `dcterms:created` |
| `environment` | SLSA `runDetails.builder.version` |
| `vegaliteChecksum` | in-toto `subject[].digest` |
| `exportIdentifier` | SLSA `metadata.invocationId`; XMP `xmpMM:InstanceID` |
| `dataChecksum` | SLSA `resolvedDependencies[].digest` |

No single standard covers the whole block. PROV, Dublin Core and XMP describe who and when but have
no place for a content digest; SLSA and in-toto have digests but no human author and no notion of a
chart expression. The block is deliberately plain JSON rather than any of these, so it stays
readable without a toolchain.
